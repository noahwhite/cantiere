# ADR-0014: Model access goes through a per-session gateway process on the worker; subscription logins stay the user's own

- Status: Accepted
- Date: 2026-10-07
- Updated: 2026-10-21 - the gateway runs in a per-session unprivileged proxy process whose confinement, channel, policy exchange and budget bounds are specified, and the build-vs-reuse evaluation of existing gateways is recorded
- Updated: 2026-11-17 - the gateway-only service's upstream hosts are those of the providers in the model secrets it holds, not hosts in the price table, and the service reaches them only through Caddy, a pinned-upstream reverse proxy that terminates the service's connection; previously the service connected directly on port 443 to addresses in an nftables set that the gateway's resolver filled
- Requirements: COST-1, COST-2, COST-3, RT-3, ID-2, ID-4, OBS-1, KN-2; open question "Do Claude Code and Codex subscription terms allow headless use from a self-hosted multi-session server?"; Phase 0 item "test broker-held subscription credentials"

## Context

Cantiere does not resell or proxy model access as a service; each user brings their own credentials (README).
Model spend must be metered per session and hard-capped (COST-1, COST-2), and denied models must be unreachable (RT-3).
The gateway parses requests and response streams that the sandbox controls, and the worker that would otherwise host it is the most sensitive component on a host (ADR-0010).

The terms differ by vendor:

- [Anthropic](https://code.claude.com/docs/en/legal-and-compliance): subscription OAuth is for ordinary use of the unmodified Claude Code binary, which an end user may sign in to even where a platform hosts it. Products, including Agent SDK integrations, must use API keys. Developers "may not collect, store, or intermediate Claude.ai credentials or session tokens".
- OpenAI: "Sign in with ChatGPT" for open-source, self-hosted apps (preview) explicitly supports [self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms.md) and passing the token to a Codex `app-server` child process. ChatGPT Plus/Pro sign-in is also supported in [opencode](https://opencode.ai/docs/providers/), so OpenAI subscriptions are not tied to OpenAI's own CLI.

## Decision

**API-key mode (default).**

- Each runtime's base URL points at the worker's model gateway: `ANTHROPIC_BASE_URL` for Claude Code, and the ACP agent's provider base URL for everything else (opencode provider `baseURL`, Codex `model_providers`). The sandbox holds only a placeholder key.
- This is how non-Anthropic and non-OpenAI models run: a persona picks an ACP agent and a model, and the gateway injects that provider's key. For example:

  ```yaml
  name: kimi-reviewer
  runtime: acp
  agent: opencode
  model: moonshot/kimi-k3
  secrets: [{provider: moonshot, ref: openbao://kv/models#moonshot}]
  github: {permissions: read, authoring: bot}
  budget: {session_usd: 5}
  ```

- A model secret is a secret entry that names its provider, as the `secrets` entry above does.
  Each provider is declared in the config repo (ADR-0017) with the upstream host the gateway sends that provider's requests to, for example `api.moonshot.ai` for `moonshot`; those declared hosts are the upstream hosts of the providers in a set of model secrets.
  A session's model secrets come from its persona; the model secrets the gateway-only service holds (below) are those the config repo declares for the server's own model calls, which the server sends it in `Init`.
- The gateway does four things:
  - injects the real key (Anthropic, OpenAI, Bedrock, Vertex, or any OpenAI-compatible endpoint such as DeepSeek, Moonshot, OpenRouter or a local vLLM);
  - rejects requests for denied models (RT-3);
  - reads token usage from responses and prices it from a per-model price table (input, output, cache read and cache write per million tokens, plus the price-affecting options below) kept in the config repo (ADR-0017), producing authoritative `cost` events (COST-1); a model with no price entry is refused, so API-key spend is never unmetered;
  - enforces budgets with reservations (COST-2): the server grants each session a budget lease from an atomic per-tenant daily counter in Postgres; before forwarding a request the gateway reserves its worst-case cost (below) from the lease, refuses the request if the reservation does not fit, and releases the unused part when the response's usage is known.
    When the lease and the daily counter are spent the session pauses to the inbox.
- The worst case is computed from the request alone, and a request whose worst case cannot be computed is refused, so nothing the guest sends can cost more than its reservation (conformance test 9b):
  - Parsing: because the request bytes are forwarded unchanged, the gateway refuses a request the provider could read differently from the gateway's own parse: a body that is not strict UTF-8 JSON, a duplicate key at any depth, and a header or query parameter given more than once.
  - Endpoints: each provider adapter allows only the synchronous inference and token-counting endpoints whose usage it parses, and model listing (for example Anthropic `POST /v1/messages` and `/v1/messages/count_tokens`, OpenAI `POST /v1/chat/completions` and `/v1/responses`, Bedrock `InvokeModel` and `Converse`, Vertex `generateContent` and `rawPredict`, each with its streaming form).
    Everything else is refused, including batches, files, fine-tuning, realtime sessions and Responses requests with `background: true`, because their cost is billed outside the response.
  - Input: a request that refers to input it does not carry (OpenAI `previous_response_id` or `conversation`, uploaded file IDs) is refused.
    Input tokens are counted with the model's tokenizer where the provider publishes it, and otherwise bounded at one token per UTF-8 byte of the request's text, including system prompt and tool definitions, plus the provider's published per-message and tool overhead; images use the provider's published token formula.
    Where that formula takes an image's pixel width and height, the proxy process reads them by parsing the sandbox-controlled image bytes the request carries, so applying it parses image data (Consequences); a formula that bills a flat amount per image needs no such parse.
    A request that carries a document is reserved at the model's maximum input from the price table (its context window), because providers bill a document by the text and page images they extract from it and publish only typical per-page figures; a model with no maximum input entry is sent no documents.
    The bound is priced at the highest input price the request can trigger: a cache write at the longest duration it asks for, and a long-context tier once the bound crosses that tier's threshold.
  - Modalities: each model's price entry lists the input and output modalities it accepts, each with its price; a request that sends or asks for a modality its model's entry does not list is refused, so an image or document is never reserved at a text price the provider does not charge for it.
    The first release accepts text, images and documents as input and text as output, and refuses audio and video; no supported runtime sends them today, although opencode is expected to once its pending audio and video attachment fix ships.
    A later release can accept them only with a bound that rests on nothing the guest asserts.
    The gateway measures each clip's duration by decoding it rather than reading its header.
    It fixes or refuses the request options that change the provider's token rate, such as frame rate, resolution and provider-run processing.
    It reserves at the provider's highest rate for the settings that remain, and prices an output limit at the audio output price when the request asks for audio output.
    A mode with no such bound stays refused.
  - Output: the request's output limit (`max_tokens`, `max_output_tokens` or `max_completion_tokens`), or the model's maximum output from the price table when the request sets none; a request without a limit for a model with no maximum output entry is refused.
    A choice count (`n`) multiplies the output bound.
  - Provider-run tools, such as web search, are allowed only when the price table prices them and the request caps their use (for example Anthropic's `max_uses`); the reservation includes that cap at the tool's price and, because a tool's results are billed as input tokens the request does not carry, the model's maximum input for each use.
    Any other provider-run tool, and a priced one on a model with no maximum input entry, is refused.
    A tool's options are listed like request fields (below), by their path at every depth, so an option that changes the tool's price, such as a search context size, is priced at every value or refused.
    A provider-run tool or request field that makes the provider contact an address the request names, such as Anthropic's web fetch tool or the Messages API `mcp_servers` field, is refused unless the operator also lists it as accepted egress, because the provider's request bypasses the egress allowlist (ADR-0011).
  - Request fields: each endpoint's request fields at every depth, path and query parameters other than the model, and request headers, including every `anthropic-beta` value, are listed in the price table, each as price-neutral or with a price for every value the provider offers, so an account default is always a listed value; a request with an unlisted field, parameter, header or value is refused, because a new provider parameter or header can change the price (for example Anthropic's `speed`, a Vertex location with a regional price, or Vertex's `X-Vertex-AI-LLM-Shared-Request-Type: priority`).
    A field inside an object-valued field is listed by its path, such as `additionalModelRequestFields.top_k` or `additionalModelRequestFields.anthropic_beta` on Bedrock `Converse`, down to the fields that hold values, and each such path is listed as price-neutral or with a price for every value the provider offers.
    An object-valued field cannot be listed as price-neutral as a whole, because a price-affecting value can sit inside it; a request that carries a nested field or value its path does not list is refused.
    Each element of an array-valued field is listed and priced as a value, the way each `anthropic-beta` header value is, so each entry of `additionalModelRequestFields.anthropic_beta` must be a listed value.
    Request text that the input bound above counts, such as message text, the system prompt and tool definitions with their schemas, is input, not a field: it is priced by that bound, while the fields around it, such as a content block's type or cache settings, are listed like any other.
    A provider account can set or change the value a price-affecting field takes, such as an Anthropic workspace's `default_inference_geo` or the project tier OpenAI's `service_tier: "auto"` selects, and the gateway cannot see it, so a request that omits such a field or sets a value the account resolves is reserved at the field's highest listed price; its usage is priced at the value the response reports, or at that highest price when the response reports none, and the unused part is released.
    A listed value that raises the model's context window, such as a long-context beta, carries its own maximum input, and a request that sets it uses that maximum wherever the reservation uses the model's maximum input; a request that sets such a value without that entry is refused if it carries a document or a provider-run tool.
    These two rules apply to a nested listed value exactly as they apply to a top-level one: a long-context beta in `additionalModelRequestFields.anthropic_beta` carries its own maximum input, as the same value in the `anthropic-beta` header does.
  - Usage: a stream that will carry no usage (OpenAI Chat Completions streaming without `stream_options.include_usage`) is refused, because the gateway does not change requests.
    A request whose final usage never arrives, because the caller or the provider ended it early, is charged its full reservation.
    Usage with a field the parser does not know is charged at least the full reservation and raises an operator alert.
  - A price the table does not list yet, such as a provider price change, is outside the reservation; the daily reconciliation against provider usage reports (below) detects it.
- The gateway forwards each provider's own API (Anthropic Messages, OpenAI Chat Completions and Responses, Bedrock, Vertex, OpenAI-compatible endpoints) without translating it.
  Apart from swapping the placeholder for the real credential and choosing the upstream, request and response bytes pass through unchanged, including unknown response fields; a request carries only listed fields, parameters, headers and values (above).
  Streams are relayed as they arrive; usage is read from the stream while relaying it, not by buffering it.
- A budget refusal gets its own error type, `cantiere_budget_exceeded`, with HTTP status 402 and a body in the provider's own error format; the adapter pauses the session to the inbox on it.
  Conformance test 9 (architecture.md) checks, for Claude Code and for each ACP agent before it is enabled for API-key sessions, that the runtime treats this refusal as final and does not retry it; if a runtime retries 402, the status is changed for all runtimes in a superseding ADR.
  The same test checks that the runtime's requests pass the rules above with the pinned runtime version, so a runtime upgrade that adds a request field, header or beta value or drops `include_usage` is caught before it reaches users.
- The price table in the config repo may be seeded from LiteLLM's MIT-licensed `model_prices_and_context_window.json`, credited in `NOTICE`; config-repo entries always win, and the missing-price rule above is unchanged.
- Keys belong to the deployment or to individual users; per-user keys are used only for that user's sessions.
  Where a provider offers projects or workspaces with their own spend limits, operators give each persona, or each user with a per-user key, its own, which bounds what a stolen key can spend (Consequences).

**Where the gateway runs: a per-session proxy process.**

- For each session the worker starts one proxy process, `cantiere-worker proxy`, a subcommand of the same static binary (ADR-0019), inside the session's network namespace.
  That process hosts the model gateway together with the session's egress proxy (ADR-0011) and git proxy (ADR-0010), so the choke point those decisions share stays one process.
  The gateway's strict JSON request parser, its tokenizers and its image parsing (above) run in this process with the rest of the gateway; the worker never parses a session's model requests.
- The process never talks to OpenBao, the server or any other secret store, and holds no credential for them.
  Secrets reach it by the chain ADR-0010 already sets, each hop holding less: secret store to server (the only store client) to worker to proxy process.
- The usage parsers, pricing, reservation logic and passthrough proxy are separate crates that do not depend on Cantiere's session types, so the gateway can be released on its own later without a rewrite.

**Confinement of the proxy process.**

- The process runs as a per-session user that is distinct from the jailer's per-VM user of the same session (ADR-0007), so a VMM escape does not reach the process's memory and a compromised process does not reach the Firecracker API or vsock sockets.
  Both users come from a uid range reserved for Cantiere, and a uid is reused only after its scope is empty and no file it owns remains.
- The worker starts the process through a single-threaded spawn helper that it forks before starting any thread.
  The helper places the child in its own systemd scope outside the worker's cgroup, gives it a new mount namespace whose root is an empty read-only tmpfs (no `/proc`, `/sys`, `/dev`, `/run`, `/var` or `/home`), moves the descriptors it was given to fixed numbers, closes every other descriptor with `close_range`, sets `no_new_privs`, `RLIMIT_CORE` to 0, `RLIMIT_FSIZE` to the journal cap, `RLIMIT_NOFILE` from the worker configuration and an `oom_score_adj` under which the kernel kills a session's proxy process before any VM or the worker, switches to the session's proxy user with no capabilities, and executes the binary from a descriptor with an empty environment and no arguments that carry values.
  The worker opens every descriptor close-on-exec and sets close-on-exec on each descriptor it takes back from systemd's store, so a process never inherits another session's channel or sockets.
- Before it reads `Init`, the process makes itself non-dumpable (`PR_SET_DUMPABLE` 0), so no core dump, `ptrace` or `/proc/<pid>/mem` read by the same user reaches its memory; applies a Landlock ruleset that grants no filesystem access; and installs its seccomp filter.
- The seccomp filter allows only the system calls the binary uses and kills the process on any other.
  It excludes `execve` and `execveat`, `ptrace`, `process_vm_readv` and `process_vm_writev`, `unshare`, `setns`, `mount`, `bpf`, `userfaultfd`, `keyctl`, `perf_event_open`, every `io_uring` call (seccomp cannot see the operations a ring submits), `clone` with namespace flags, and `socket` for any family other than `AF_INET` and `AF_INET6`, so the process cannot open Unix, netlink, packet or vsock sockets; `clone3` returns `ENOSYS`, because seccomp cannot inspect its flags.
  The filter is generated with the binary and tested against it (conformance test 9a).
- Secret values are kept in `memfd_secret` memory where the kernel provides it and in locked pages otherwise, and are zeroed on `SecretUpdate`, `SecretRevoke` and exit.
- The scope sets `MemoryMax`, `MemorySwapMax=0`, `TasksMax` and `CPUQuota` from the worker configuration; a scope carries no execution settings, so the descriptor, core and file-size limits and the OOM score come from the spawn helper (above); these resources count toward the session's quotas (COST-4).
  Inside them, the process caps concurrent guest connections, header and body sizes, GraphQL document size, and the bytes and compression ratio a pushed pack may inflate to during the secret scan; a request over a cap is refused with a `Denial`.
  An error or panic while handling one guest connection ends that connection, with its end record or denial, not the process.
- The namespace's output chain matches the proxy user's packets and drops them by default.
  It first accepts packets of established connections, which includes the process's replies to guest connections, DNS to the worker resolver's two addresses (the guest's and the proxy's, below), and new TCP connections to each declared private model upstream (below).
  Before any other rule that allows a new connection it drops every non-global address range (RFC 1918, `100.64.0.0/10`, loopback, link-local, unique local, IPv4-mapped and NAT64 prefixes, documentation and reserved ranges), the cloud metadata addresses listed below, the host's own addresses, and the addresses of the server, OpenBao, Postgres and the object store.
  It then allows new TCP connections to ports 80 and 443 only to addresses in a per-session set that the resolver fills with its answers for allowlisted names and for the upstream hosts of the providers in the session's model secrets, each for the answer's TTL.
  The guest reaches its models through the gateway's base URL, so those upstream hosts are not on its allowlist; the resolver answers them only on a second listening address that the proxy process gets in `Init` and the guest's rules do not reach, and on the address the guest uses it answers only allowlisted names (ADR-0011).
  The resolver refuses any answer that is an IPv6 address, is in a non-global range or is at a cloud metadata address listed below, which closes DNS rebinding through an allowlisted wildcard, and refuses the names of platform services, since services behind a CDN share addresses with allowed sites.
  A model upstream on a private address, such as a local vLLM, is declared in the config repo with its address and port, and only that address and port is accepted, ahead of the drops.
  The config check refuses any IPv6 address, including an IPv4-mapped one such as `::ffff:169.254.169.254`, and any other address that does not parse as dotted-decimal IPv4.
  No model upstream needs IPv6, and refusing the whole family leaves no IPv6 form that could carry or reach a refused address.
  It refuses an IPv4 address that is a loopback address, a "this network" address (`0.0.0.0/8`), a link-local address, the host's own address, a platform service's address, or a cloud metadata address.
  The cloud metadata addresses are an explicit list, because not every metadata service is link-local: `169.254.169.254` (the instance metadata service of AWS, Azure, Google Cloud and others), `169.254.170.2` (AWS ECS task credentials), `169.254.170.23` (AWS EKS Pod Identity), `100.100.100.200` (Alibaba Cloud metadata) and `168.63.129.16` (Azure WireServer).
  There is no override.
  A declaration at any other private IPv4 address, such as an RFC 1918 address or a `100.64.0.0/10` address that none of these rules refuses, is accepted, and its address and port are reachable from the process.
  The guest's traffic never uses this chain: it reaches the process through the redirect and the listening sockets (ADR-0011).

**Channel between the worker and the process.**

- Introduction needs no tokens: possession of the channel is the credential.
  The worker creates a `SOCK_SEQPACKET` Unix socket pair, so each message is one datagram and no restart can leave a partial frame, together with the namespace's listening sockets (so the process needs no privilege to bind ports 80 and 443) and the two journal files (below), and passes them to the spawn helper.
  It keeps a pidfd for the process and sends `Init` as the first message; values stay in the process's memory, never on disk, in argv or in its environment (ID-4).
- The channel follows high-side and low-side rules: the worker is the high side and only pushes; the process is the low side and only reports.
  - Down (worker to process): `Init` (protocol version, session ID, a random instance ID, that session's secret values with their injection rules, the per-session CA key, the budget lease, the session's domain allowlist with each domain's mode, the upstream trust roots, the resolver address, for the gateway-only service its listener map, the liveness bound and the drain bound used on end of file), `SecretUpdate` and `SecretRevoke` (replace or remove one value, for refresh such as the hourly GitHub token and for revocation such as an unlinked user's token, ADR-0010, ADR-0012), `PolicyUpdate` (replaces the allowlist and modes and drops every cached decision, for example when an operator approves a repo-layer egress entry or a persona's permissions change), `ListenerUpdate` (replaces the gateway-only service's map from upstream host to listener address and port), `LeaseTopUp`, `StartDecision`, `RecordAck`, `JournalFree`, `Resync`, `Heartbeat` and `Stop`.
    A secret update applies to requests the process forwards after it, without restarting the process.
    On `SecretRevoke` the process drops the value and refuses every request that would use it and has not yet been forwarded, including requests waiting for a `StartDecision`; it sends an end record marked not forwarded for each request that has a start record, and a `Denial` for each that does not; requests already forwarded are not cut.
    The worker chooses what to send from the references the persona declares (ID-3); nothing the process sends changes which secrets it gets.
  - Up (process to worker): `Hello`, `StartRecord`, `EndRecord`, `Denial` and `JournalSwitch`, nothing else; the gateway-only service adds `ListenerAck`, which answers a `ListenerUpdate`.
    No message lets the process name a secret, ask for a larger lease, change its own policy, or refer to another session.
  - The worker treats every upward message as untrusted input: it checks the schema, size and value ranges, accepts an `EndRecord` only for a request ID with a start record from this process, and scrubs records before relaying them (ADR-0010).
    A message that fails these checks stops the process, with the same effect as a crash (below), and raises an audit event.
  - Rate is handled by backpressure, not by stopping: the process limits its own start records and denials with per-session token buckets set below the worker's limits, and when a bucket is empty it stops reading guest requests rather than dropping or merging records; if the worker's limit is still exceeded, the worker stops reading the channel until the rate falls.
  - These checks cannot prove that a reservation or a usage report matches what was sent to or returned by the provider: the process holds the key and is the only component that sees the traffic.
    The budget cap therefore holds against the guest, not against a compromised proxy process, which could under-report and spend up to whatever the provider allows for that key (a gateway inside the worker would have the same limit, running as root).
    Two backstops do not depend on the process: operators set provider-side spend limits on each key where the provider offers them, and the server compares recorded cost per key each day with the provider's usage reports where available and raises an alert on a difference.
  - The messages are protobuf contracts (ADR-0004) with the session ID fixed by the channel, not taken from the message.

**Policy decisions and records.**

- Every model request, every request the process forwards on an `inspect` or `inject` domain, and every push is a policy action (ADR-0015).
  The domain allowlist and modes are data from `Init` and `PolicyUpdate`, applied by the process as the resolver applies them; method, path, operation and push rules are decided by the server's `policy.Decide`, never by the process.
- Before it forwards such a request, the process sends a start record: a random 128-bit request ID and the normalized action, which is the method, host and path, the GraphQL operation type and name for a GraphQL call, the ref with its old and new head SHAs for a push, and the model and reservation for a model request.
  The server decides, appends the audit row with the action, target, head SHA and decision (SEC-5), and returns the `StartDecision` through the worker; the process forwards the request only after an allow, and records a denied one as not forwarded.
- For a read-only action the decision may be cacheable, with a key (host, method and path pattern) and a TTL (ADR-0015).
  The process then decides matching requests from its cache without a round trip; it writes each one's start record to the journal before forwarding it and sends it afterwards, so the audit log still has every request.
  Such a start record is marked as decided from the cache, and the server records it under that cached decision whatever the session's state when it arrives; the rejection of starts after a session ends (below) applies only to starts waiting for a decision.
  Whether the request was forwarded comes from its end record, and a cached start with no end record is recorded with its outcome unknown.
  Cached decisions never cover a write, a push or a model request; they expire at their TTL, `PolicyUpdate` drops them, and while the worker or server is unreachable they are honoured only until their TTL ends (ADR-0003).
- The decision for a push carries the data ADR-0012's push checks need at that moment: the commit identity and its chosen address, the key fingerprints the server recorded for the session and has not deleted, the identity's long-lived key fingerprint where the fallback applies, and the user to credit.
  The server's address recheck before each push is part of that decision, so a failed recheck is a denial.
- The server accepts a start only while the session is running and, for a model request, while its lease covers the reservation, so a session that ended while the worker was down cannot start a model call after reconnecting.
  Start records are idempotent by request ID: the process resends an unanswered start after a `Resync` (below), and the server returns its first decision only while the session is still running; once the session has ended it rejects every start, including a resend of one it had accepted, and records that request as not forwarded.
  If the caller has gone away before the decision arrives, the process sends an end record marked not forwarded, which releases the reservation.
- When a request ends, the process appends an end record with the same request ID (status and, for a model request, the usage and cost) to the per-session journal, then sends it; the worker reads the journal when it adopts or restarts the process and resends what the server has not acknowledged, and the server ignores a second end record for the same request ID.
  The process scrubs every record with the session's secret values, using the worker's scrubber (ADR-0010), before writing it, so the journal holds only request IDs, statuses, usage, cost and scrubbed denial details, never secrets or request or response bodies, and the worker deletes both journal files when the session's records are all acknowledged.
  The worker scrubs and relays both records to the server as before (ADR-0010, ADR-0015).
- Each request the process refuses itself (allowlist, size caps) is an individual `Denial` with its own random 128-bit request ID, written to the same journal and sent the same way, without a start record, and the server ignores a second denial with the same ID (ADR-0011, SEC-2).
  The worker relays a session's records in batches, and the server appends each batch to the tenant's audit chain in one transaction, so a burst of denials takes the chain lock (ADR-0015) once per batch, not once per record.

**Journal.**

- The journal is a pair of files: the worker creates both with `O_NOFOLLOW` and `O_EXCL` in a root-owned per-session directory and passes the process a write-only `O_APPEND` descriptor for each; `RLIMIT_FSIZE` holds each to its size cap in the kernel, whatever the process does.
- The process appends to one file at a time, so a long session never fills the journal and no file is truncated while it is written.
  When the active file passes half its cap and the other file is free, the process moves to the other file and sends `JournalSwitch`.
  The worker then reads the file the process left to its end and resends what the server has not acknowledged; once all of it is acknowledged, the worker truncates that file to zero and sends `JournalFree`, and only then may the process move back to it.
  An honest process never writes a file it has moved off, so the truncate cannot lose one of its records.
- The journal lets an honest process's records survive its own crash and a worker outage; a compromised process can rewrite or omit its own records, as it can misreport anything else (above).
- Records in the journal are length-prefixed and checksummed frames.
  The worker parses the journal as untrusted input with the same checks as channel messages, stops at the first frame that fails them, raises an audit event, and leaves every request after that point to the server's rule for start records without end records (below).
- The process reads a request from a guest connection only after reserving journal space for every record it may write about it: its denial or its end record, and its start record when it is decided from the cache, so every request it has read can always be recorded.
  When no space is left, the process stops reading requests from every guest connection, open or new, until the worker frees a journal file, so a guest cannot exhaust the process's memory or disk during a worker outage, and no denial or end record is summarised or dropped.

**Lifecycle and re-adoption.**

- The process runs in its own systemd scope outside the worker's cgroup, like the session's VM (ADR-0003), so restarting or upgrading the worker does not cut in-flight model streams.
  While the worker or the server is unreachable, no start record can be accepted, so the process forwards no new request that needs a decision; streams already in flight finish and write their end records to the journal.
- The worker service sets `Restart=always`, `FileDescriptorStorePreserve=yes` and a `FileDescriptorStoreMax` of at least two per session at its maximum session count.
  It stores each session's channel end and the process's pidfd with `FDPOLL=0`, under a name that holds the session ID, the instance ID and the protocol version, so the store survives a restart, an upgrade, a crash and a worker that has run out of restart attempts.
  The worker removes a session's entries (`FDSTOREREMOVE`) only after it has stopped that process and collected its journal.
- On start the worker takes each entry back and re-adopts the process:
  - It sends `Resync` with a fresh random 128-bit nonce, since the process cannot see a worker restart on a channel that stayed open.
    On `Resync` the process forgets which files were free, so it stays on its active file until the new worker sends `JournalFree`.
  - The process answers `Hello` with that nonce, its protocol version, session ID, instance ID and the journal file it is writing, then resends its unanswered start records.
  - The worker accepts `Hello` only if the `SCM_CREDENTIALS` the kernel attaches (it sets `SO_PASSCRED` on its end) carry the session's proxy user and the pid of the stored pidfd, and that process is still alive, which rules out pid reuse; and only if the session ID, instance ID and protocol version match the stored name exactly.
    `SO_PEERCRED` is not used, because on a socket pair it reports the worker that created the pair.
  - A worker that does not speak the stored protocol version stops the process and starts a new one; it never accepts another version from a running process, so a compromised process cannot pick an older validator.
  - The worker then reads the journal, resends the end records the server has not acknowledged, and sends `JournalFree` again for each journal file that is free, since a worker that restarted may have truncated a file without sending it; it never truncates the file `Hello` names, and truncates the other only once all of it is acknowledged; the process cannot move to that file before the `JournalFree` that follows, so no record is written to a file while the worker may truncate it.
  On any failed check, and for any proxy scope whose entries are missing, the worker stops the process and starts a new one, as after a crash (below).
- The process sees end of file on the channel only when no copy of the worker's end is left, for example after the store was lost.
  The store keeps the channel open even when the worker has stopped for good, so the worker also sends `Heartbeat` at an interval well inside the liveness bound from `Init`, and the process treats a channel silent for longer than that bound as end of file; the bound is set longer than a worker restart or upgrade takes, so those do not cut streams.
  On end of file the process stops accepting connections and reading requests, lets forwarded requests finish within the drain bound from `Init`, writes their end records, zeroes its secrets and exits.
- If the process exits, the session's egress stops, because nftables still redirects only to it (fail-closed).
  The worker restarts it with the session's secrets and the remaining lease, after collecting its journal.
  The server counts the full reservation of every request that has a start record and no end record as spent, so a crash can over-count spend but never under-count it, and every such request still has its start record in the audit log.
  Provider usage reports are not per request, so an over-counted reservation is not given back; because a failure in one connection does not end the process and rate excess throttles instead of stopping it, the guest can cause this only through a defect that kills the process.

**Gateway-only mode beside the server.**

- Model calls the server makes itself, outside any session (KN-2, KN-3, KN-4), go through the same binary run as its own systemd service, `cantiere-gateway`, under its own user, never the server's, so it cannot read the server's OpenBao AppRole credential; systemd starts it, not the server.
  It has a lease from a per-tenant system budget, and the same message set, budget rules and journal, with the server as the high side.
- It applies the same non-dumpable setting, Landlock ruleset, seccomp filter and secret memory as the session process.
  In place of the spawn helper, its unit gives it an empty read-only root with only the binary (`TemporaryFileSystem=/`), `PrivateDevices`, `ProtectProc=invisible`, `MemoryMax`, `TasksMax`, `LimitCORE=0` and `LimitFSIZE` at the journal's size cap, which holds each journal file to that cap in the kernel as `RLIMIT_FSIZE` does for a session process.
  Its unit passes its two journal files with `OpenFile=` in append mode; `systemd-tmpfiles` creates them in a root-owned directory, owned by the gateway's user with mode 0660 and the server's group, so the server, as the high side, can read and truncate them but cannot replace them with a link.
- In place of the session chain, the gateway-only service reaches upstream hosts on global addresses only through a local egress reverse proxy, Caddy, run by a companion unit, `cantiere-gateway-egress`, under its own user.
  The proxy has one listener for each of the upstream hosts of the providers in the model secrets the gateway-only service holds (API-key mode, above; ADR-0017), and each listener's upstream is that hostname on port 443, fixed in the proxy's configuration.
  Under systemd each listener is on a loopback address and is held by a socket unit, `cantiere-gateway-egress.socket`, which passes it to the proxy, so a restart of the proxy service, as distinct from the socket unit, never releases a port another local process could bind; under Compose each listener is on the proxy container's address on the gateway's network, which holds only the gateway and the proxy.
  The gateway gets each host's listener address and port in `Init`, since its empty root holds no proxy setting, and sends each request for an upstream host as plain HTTP to that host's listener, over loopback under systemd and across the gateway's network under Compose.
  The proxy opens TLS to the listener's hostname on port 443 only, sets the SNI and the `Host` header to that hostname itself, and verifies the server certificate against that hostname.
  So the gateway chooses neither the destination, the SNI nor the `Host`: a request that names another host, in its `Host` header or as an absolute URI, still reaches only the listener's hostname, under that hostname, and no listener exists for a host outside that list.
  Host nftables output rules for the gateway's user accept established connections, new TCP connections to the proxy's listeners, and new TCP connections to each declared private upstream's address and port, and drop all other outbound traffic, so the service's firewall drops every direct connection from the gateway to any other address, including an address shared with a permitted upstream host, for example behind the same CDN.
- The proxy terminates the gateway's connection, so it sees the model requests, their bodies and the provider keys in plaintext; that cost is stated under Consequences.
  What it enforces is the pinned upstream of each listener, not anything the gateway sends.
- The proxy is Caddy, pinned at v2.11.9; no release before v2.11.5 is used ([GHSA-6365-7ppr-5r92](https://github.com/caddyserver/caddy/security/advisories/GHSA-6365-7ppr-5r92)).
  Its generated configuration:
  - keeps upstream certificate verification on, as it is by default, and leaves the TLS server name at its default, the upstream's hostname;
  - sets the upstream `Host` header on each listener explicitly to the bare hostname, with no port, since Caddy's default for an HTTPS upstream is the upstream's host and port;
  - names each upstream in the `tcp4/` network form, so the proxy never dials IPv6;
  - sets `network_proxy none` on each upstream transport, so the proxy ignores any `HTTPS_PROXY` setting in its environment;
  - turns the admin endpoint off;
  - removes every request header that carries a provider key, such as `X-Api-Key`, from every logger, the access log and the error log alike, with a `filter` encoder that deletes `request>headers>X-Api-Key` for each such header in its canonical form, since Caddy attaches the whole request to each error entry, for example the 502 an upstream TLS or connection failure produces, and by default redacts only `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie`.

  Caddy has no filter on the addresses it resolves, so the refusal of private and metadata addresses rests on the certificate check against the pinned hostname and on the proxy's firewall rules (below).
- The proxy's configuration is generated, not written by hand: when the server loads the config repo, and again after any config-repo change that alters the set of hosts, it writes one listener for each upstream host of the providers in the model secrets the gateway-only service holds, as an exact hostname with no wildcard and no address, with port 443 only, and the same hosts as the resolver's name list.
  It writes both atomically to files in a directory owned by the server's user, which the proxy's user and the resolver's user can read but not write; the resolver reloads its list without a restart, and a systemd path unit triggers a oneshot unit when its configuration changes, since its admin endpoint is off and a path unit alone does not restart a running service; under systemd the generator also writes the socket unit's `ListenStream=` entries, one for each listener in the order the proxy's configuration maps them to its inherited descriptors (`fd/3` onward), and the oneshot unit runs `systemctl daemon-reload` and then `systemctl restart cantiere-gateway-egress.socket cantiere-gateway-egress.service`, because a socket unit's listeners change only when the socket unit restarts.
  A change to the set of hosts runs in this order, so the gateway sends nothing to a listener while its sockets are being replaced: the server sends the gateway a `ListenerUpdate` with an empty map, and the gateway holds every new request for an upstream host, waits until each request and connection already using the old map has finished or been closed, and then answers with `ListenerAck`; only after that acknowledgement are the host rules that admit the gateway's connections to the proxy's listeners removed; the proxy's configuration and socket unit are replaced and both units restart; the host rules are then regenerated from the same file, and the server sends the new map in a second `ListenerUpdate`; if either unit fails to restart, the procedure stops with the host rules still removed and no new map sent.
  A listener address is never reassigned: an address belongs to one upstream host for the life of the deployment, a removed host's address stays unbound and is never given to another host, and the generator refuses a configuration that would reuse one, so a request built from an old map can never reach a different host's pinned upstream.
  The same applies at install and boot: the socket unit is bound before the gateway starts, and the rules that admit the listeners are loaded only after it is.
  A config-repo check refuses a provider upstream host that is an IP address, holds a wildcard or names a port.
- The egress proxy is a separate component from the session egress proxy of ADR-0011, which is unchanged.
  The session egress proxy serves the sandbox: it intercepts transparently, applies per-session allowlists that change while the session runs, terminates TLS with the per-session CA for `inspect` and `inject` domains and journals denials to the audit log.
  The gateway-only service needs none of that: its calls are the server's own, so it addresses the proxy's listeners directly, and its upstreams are a fixed list of provider hosts.
- The proxy's unit has the gateway's hardening without the gateway's own Landlock ruleset and seccomp filter: an empty read-only root with only the proxy's binary, its generated configuration and the system's CA certificates, `PrivateDevices`, `ProtectProc=invisible`, `NoNewPrivileges`, no capabilities, a systemd system call filter, `MemoryMax`, `TasksMax` and `LimitCORE=0`.
  Host nftables output rules for the proxy's user run in the session chain's order: accept established connections and DNS to the gateway's resolver; drop the same address ranges and every IPv6 destination; then allow new TCP connections to port 443 only to IPv4 addresses in a set its resolver fills with its answers for the upstream hosts of the providers in the model secrets the gateway-only service holds (API-key mode, above; ADR-0017), each for the answer's TTL.
  The proxy's own egress is therefore TCP 443 to global IPv4 addresses and DNS to its resolver; private, `100.64.0.0/10`, link-local and loopback destinations other than its resolver are dropped.
  That set is a second layer under the pinned listeners, so a compromised proxy still reaches only port 443 on global addresses the resolver returned for those hosts; the proxy parses only the gateway's requests and the upstreams' responses, never sandbox-controlled bytes.
- The gateway's resolver is the worker's resolver (ADR-0011), with the same refusals, answering only the names in the generated name list, run by a second companion unit, `cantiere-gateway-resolver`, under its own user, and it listens on a loopback address and an unprivileged port, since it holds no capability to bind port 53; under systemd the egress proxy is configured with that address and port as its only resolver, and under Compose its resolver is Docker's, as below.
  A process holding `CAP_NET_ADMIN` in the host network namespace can rewrite the whole host ruleset, and seccomp cannot inspect netlink messages, so the process that parses DNS holds no capability.
  The resolver's unit starts a set updater with only `CAP_NET_ADMIN`; it opens its netlink socket, makes itself non-dumpable, and starts the resolver as a child over a socket pair; the child drops every capability before it reads any network input, and its seccomp allowlist has no `ptrace` or `kill` calls and allows `socket` only for UDP and TCP over IPv4 and IPv6, so it queries from a random source port and retries a truncated answer over TCP but cannot open a netlink socket.
  Host output rules for the resolver's user accept established connections, which carry its answers to the egress proxy, and allow new connections only for DNS to the host's upstream resolvers.
  The child sends each accepted answer to the updater as a fixed-size record (address family, address, TTL); the updater reads nothing else, refuses a record whose address is in a non-global range or is a platform address, and adds the address to that one set with a fixed netlink request whose timeout is the TTL raised to a floor of one second and capped; a zero TTL is valid DNS but a zero timeout means the element never expires.
  The set has a fixed maximum size, so a compromised child cannot grow it without bound; when it is full, lookups fail until entries expire.
  The child answers the egress proxy only after the updater confirms the address is in the set, so the proxy's first connection is not dropped.
  Both processes have the gateway's empty root, Landlock ruleset and their own seccomp allowlists, so a crafted DNS answer that compromises the child can only add global addresses that are not platform addresses to the set, each for at most the TTL cap, and cannot change any other rule.
- A Java process cannot hand a socket pair to a process it did not start, so the channel is a Unix stream socket that a systemd socket unit creates, owned by the server's user with mode 0600, and passes to the gateway as a listening descriptor; accepting on it needs neither `socket()` nor filesystem access, so the seccomp filter and Landlock ruleset still apply.
  The gateway accepts one connection at a time, and only if `SO_PEERCRED` reports the server's user; on a connected socket, unlike a socket pair, `SO_PEERCRED` reports the peer.
  Java's Unix-domain channels are stream sockets, so messages are length-prefixed; a server restart closes the connection, and the next one starts with `Resync` and `Hello` as a re-adoption does.
  While no server is connected the gateway forwards no new request; requests in flight finish and write their end records to the journal.
- The server sends model requests to a second socket created and passed the same way, on which the gateway applies the same `SO_PEERCRED` check.
- In the Compose deployment (ADR-0019) the gateway is its own container: a non-root user, a read-only root filesystem, every capability dropped, `no-new-privileges`, so runc loads the seccomp profile only just before it starts the entrypoint, a Docker seccomp profile made of the gateway's filter plus the calls runc makes between loading the profile and starting the entrypoint (including `execve`) and the setup calls the gateway makes before it installs its own filter (below), such as creating and binding `AF_UNIX` sockets and the Landlock and seccomp calls, memory and process limits, a file-size limit (`ulimits: fsize`) at the journal's size cap, and its own network, not the one that reaches Postgres, OpenBao or MinIO.
  The egress proxy is its own container too, with a non-root user, a read-only root filesystem, every capability dropped, `no-new-privileges` and memory and process limits; it is the only other container on the gateway's network, and it reaches upstream hosts through a second network of its own.
  The gateway sends its requests for upstream hosts as plain HTTP to the proxy's listeners, as under systemd, but across the gateway's network instead of loopback; the proxy uses the same generator, with the proxy container's address for its listeners and Docker's upstream resolvers for its resolver, and the server writes the generated configuration to a volume mounted read-only in the proxy's container, and the operator restarts the proxy's container after a change to the set of hosts, as the Compose documentation states.
  A separate network does not stop traffic to the host's addresses or to ports published on them, so the deployment adds host firewall rules for both networks.
  For the gateway's network: in Docker's `DOCKER-USER` chain, accept its forwarded traffic to each declared private model upstream's address and port and drop all its other traffic that leaves that network, so the gateway reaches the proxy and nothing else directly; in the host's input chain, drop everything from it; and start the gateway's container with an explicit `dns` setting that names a non-loopback address, because Docker's embedded resolver forwards a query from the host's own network namespace, outside both chains, when its upstream is a host-loopback address, and a compromised gateway could carry a key out in a query name; the gateway addresses listeners by IP and needs no name resolution, so its forwarded DNS to that address is dropped by the rule above.
  For the proxy's network: in Docker's `DOCKER-USER` chain, accept its forwarded DNS to the Docker daemon's upstream resolvers, which Docker's embedded resolver sends from inside the container's network namespace unless that resolver is on the host's loopback; then drop its forwarded traffic to every other non-global range, to the host's addresses and to the addresses of an external Postgres, OpenBao or object store, as the systemd units' rules do; then accept new TCP connections to port 443 and drop the rest of its new forwarded traffic; and in the host's input chain, accept only its DNS to an upstream resolver on the host's own address and drop everything else from it.
  The Compose documentation ships these rules, and without them neither network is confined.
  These rules cannot follow DNS answers, so in Compose the proxy's container can reach port 443 on any global address; the gateway still reaches only the proxy's pinned hosts, because its own direct traffic is dropped, and a compromised gateway there can send its provider keys only to those hosts unless it also compromises the proxy; the Compose documentation states this.
  Without systemd, the gateway creates its two sockets and its two journal files itself, creating a journal file only if it is absent and otherwise reopening it in append mode, never truncating it, so a restart keeps unacknowledged records, on a volume mounted only in the gateway and server containers, and keeps the `SO_PEERCRED` check; the journal files are created with mode 0660 and a group that only the server container's user shares, so the server can read and truncate them; the server opens each with `O_NOFOLLOW` and checks that it is a regular file owned by the gateway's user, since the gateway can write that volume.
  Only then does it make itself non-dumpable and apply the same Landlock ruleset and seccomp filter as the session process, so from that point `execve` and a new Unix socket kill it.

**Subscription mode (opt-in, single-subscriber deployments only, COST-3).**

- Available only where the subscriber is the deployment's operator and the sandboxes run on infrastructure only they control, which matches Anthropic's "user signs in to the unmodified binary" allowance and OpenAI's "remote runtime only that user controls" wording most closely. Multi-user deployments cannot enable it.
- Claude: the subscriber generates their own token with `claude setup-token` and stores it in their own secret-store scope. Cantiere places it in the environment of that subscriber's sessions as `CLAUDE_CODE_OAUTH_TOKEN`, for the unmodified `claude` binary only. Storing the token is unavoidable for disposable sandboxes; this residual terms risk is stated in the setting's description.
- Claude token lifecycle:
  - `claude setup-token` prints a one-year OAuth token and saves it nowhere; Claude Code reads it from `CLAUDE_CODE_OAUTH_TOKEN` in each session ([authentication](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token)). The docs do not describe refreshing it, so Cantiere treats it as fixed until renewed; conformance test 6a (architecture.md) checks this against the pinned CLI version. The interactive `/login` credential is not used: Claude Code refreshes it automatically and updates it in place in the CLI's credential store, so keeping it valid across disposable sandboxes would mean collecting the updated credential after every session.
  - When the subscriber stores the token, the UI requires its mint date, prefilled with today for the subscriber to confirm, and the server records mint date plus one year as the expected expiry next to the secret reference in Postgres; the token value itself lives only in the secret store. The recorded expiry is an estimate; the mid-session failure path below is the backstop for a token that stops working earlier.
  - Fourteen days and again three days before the expected expiry, the subscriber gets an inbox item and a push notification asking them to renew.
  - A subscription session does not start with a token past its expected expiry; it waits in the inbox with a renew action. It never falls back to API-key mode on its own, because that changes who pays.
  - If the token expires or is revoked mid-session, the adapter detects the authentication failure from the stream-json output (a `system/api_retry` event with `error` `authentication_failed`, or an error `result`; the exact signal for a revoked `setup-token` is pinned by conformance test 6a) and pauses the session to the inbox instead of failing it. After renewal the session resumes with `--resume` (ADR-0009) in a `claude` process started with the new token.
  - Renewal: the subscriber runs `claude setup-token` on their own machine and replaces the value in their scope through the UI, which writes it to the secret store without logging it. Running sessions keep the old token until they end or pause. Cantiere cannot revoke the old token; the subscriber removes it in their Claude account settings (Claude Code section), which is also the first step after a suspected theft.
  - Credential isolation: in subscription sessions the guest environment sets none of `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` or `CLAUDE_CODE_USE_BEDROCK`/`_VERTEX`/`_FOUNDRY`, which either outrank `CLAUDE_CODE_OAUTH_TOKEN` or would send the traffic to the gateway. The adapter launches `claude` with `--setting-sources user` and `--strict-mcp-config --mcp-config <file generated from the org layer's mcp_servers>`, which holds only the servers the session's repo layers name and the org layer grants to those repos (ADR-0008). These flags keep the target repository's `.claude/settings.json` (its `env` block, `apiKeyHelper` and hooks) and `.mcp.json` from loading; Cantiere writes the user settings from the org layer's `claude.settings`, and blueprint MCP servers load only through `--mcp-config`; a repo layer cannot supply either (ADR-0008). Before the first turn the adapter runs `claude auth status` and fails the session closed unless `authMethod` is `oauth_token`. This check guards the launch only: Claude Code reloads changed settings mid-session, so guest code can still add an `apiKeyHelper` to the user settings, just as it can read the token (Consequences). The adapter re-checks the credential source in the `system/init` event on every resume and pauses the session if it has changed.
  - The adapter never passes `--bare`, because bare mode does not read `CLAUDE_CODE_OAUTH_TOKEN`.
  - The token can make only model requests, so claude.ai connectors and Remote Control are unavailable in subscription sessions; MCP servers configured by the blueprint still work.
- Cantiere never routes subscription traffic through the gateway, never intercepts it (`pass` mode in ADR-0011), and never uses it with the Agent SDK.
- ChatGPT: the user's sign-in follows OpenAI's self-hosted flow, and the token is passed to the ACP agent in that subscriber's sessions (`codex-acp`, which runs the Codex `app-server`, or opencode).
- Spend for subscription sessions is a notional API-equivalent figure from runtime-reported usage (Claude Code `result` events, ACP `usage_update`), priced from the same table and marked as runtime-reported (ADR-0009). Provider usage windows are tracked separately, and budgets apply to the notional figure.
- This answers the Phase 0 question about broker-held subscription credentials: Cantiere stores the subscriber's own `setup-token` in the secret store and places it in the guest environment of that subscriber's sessions; it never proxies, refreshes or shares it. Whether this counts as intermediating under Anthropic's terms is a residual risk the project owner accepted on 2026-10-08 for the first release of subscription mode; a change to Anthropic's terms or guidance reopens it. The alternative with no stored token is a per-session `/login` through native-terminal take-over (ADR-0013). COST-3's exception to ID-2 is permanent for subscription mode, and the docs say so.
- Subscription mode is disabled by default; the operator enables it after reading the vendor terms, linked from the setting.
- The model deny list (RT-3) cannot be enforced outside the sandbox in subscription mode, because that traffic is not intercepted; only the adapter enforces it.

## Consequences

- API-key sessions get hard budget enforcement outside the sandbox; subscription sessions get best-effort enforcement only (the adapter interrupts at the cap, the gateway cannot).
  "Hard" is in COST-2's sense: nothing the guest does, short of compromising the proxy process, can spend past the cap, apart from a price the price table does not list yet.
  The cost is refusals: a request near the cap whose worst case does not fit is refused even if its real cost would fit, input for providers without a published tokenizer is reserved at one token per byte, so such sessions are refused earlier near the cap, and batch, background, unbounded and usage-less requests are not available to API-key sessions at all.
  A request with a document, and each provider-run tool use, reserves the model's full context window of input, so a persona that uses them needs a session budget above that; a web search persona with `max_uses` of 10 on a 200,000-token model at $3 per million input tokens reserves $6 of input for the searches alone.
- A compromise of the proxy process, through a bug in the code that parses sandbox-controlled bytes (TLS, HTTP, GraphQL, git push commands and packs, request bodies in the strict JSON request parser, request text in the tokenizers, image data for the image token formula, or model response bodies and streams, including their usage, and, once a later release accepts them, audio and video), is outside the budget guarantee, as an escape into the worker would have been with an in-worker gateway.
  It does not reach the worker's host privileges, the VM, the platform's services or other sessions' processes, but it does reach every secret the session holds, and some of those reach further than the session:
  - A deployment-wide provider key works outside the gateway, from anywhere, up to the provider-side limit on that key, and spending to that limit stops the model calls of every session that uses the key; per-persona or per-user keys with their own provider spend limits (above) narrow this to one persona or user.
  - The session's installation token reaches the session's target repos with the persona's permissions until it expires within the hour.
  - In `user` mode, the linked user's access token reaches every repo both the user and the installation can, with the user's permissions, because GitHub does not keep the `repository_id` narrowing on refresh (ADR-0012), until it expires within eight hours.
  - The lease lets it spend no more through the gateway, but the keys above are not bound by the lease; provider limits and daily reconciliation bound and detect that spend (above).
- The gateway-only service's egress proxy sees the server's model requests, their bodies and the provider keys in plaintext, and so does the hop to it, over loopback under systemd and across the gateway's network in Compose; a compromise of the proxy reaches those keys.
  This cost is accepted because only a proxy that terminates the connection can fix the destination, the SNI and the `Host` itself (Alternatives considered).
- The worker and the proxy process need a small protocol for secrets, policy, lease top-ups and start and end records, plus a per-session pair of journal files; each session costs one more process and one more uid.
- Every request that needs a policy decision and has no cached one waits for one round trip to the server before it is forwarded, and stops being forwarded while the worker or server is unreachable; model calls already in flight are not affected.
- Workers, and a host that runs the gateway-only service, need Linux 5.13 or later for Landlock, workers need systemd 254 or later for `FileDescriptorStorePreserve`, and a gateway-only host needs systemd 253 or later for `OpenFile=`; `memfd_secret` is used where the kernel enables it.
- Cantiere maintains the gateway itself: each provider's usage format, including streamed and cache-token usage, and the price table must track provider changes.
  Because requests are not translated, a new provider parameter, header, beta value or service tier needs no code change, only a price-table entry in the config repo, since the gateway refuses a request field, parameter or header it does not list; a change to how usage is reported needs a code change.
- A subscription token in a compromised sandbox is exposed for its lifetime (up to a year for `setup-token`), or until the subscriber removes it in their Claude account settings. The token is in the `claude` process environment, so anything that runs in the guest, including the agent's own shell commands and code from the target repository, can read it; turning off project settings and repository MCP servers (above) removes only the paths that run before the first turn. Mitigations are egress allowlisting (ADR-0011), the git proxy's secret scan (ADR-0010), and the single-subscriber restriction. The scrubber catches only literal and known-pattern copies, not encoded ones.
- `pass` domains, including subscription endpoints, are opaque to the proxy, so guest code can send data there with credentials of its own (ADR-0011). Each `pass` entry, and each provider-run tool or request field listed as accepted egress (above), is an operator-accepted exfiltration channel and is listed in the approval diff.
- Subscription sessions do not load the target repository's Claude Code settings, hooks or `.mcp.json`; a repository that relies on them needs the equivalent in the org layer of the blueprint (ADR-0008).
- Subscription mode needs the subscriber about once a year to renew the token; a missed renewal stops that subscriber's subscription sessions, not API-key sessions.
- Concurrency limits for subscription use are not defined by the vendors; Cantiere exposes a per-user concurrent-session cap for subscription mode.

## Alternatives considered

- **[Tailscale Aperture](https://tailscale.com/docs/aperture/how-aperture-works) as the model gateway** (evaluated 2026-10-13): Aperture holds provider keys centrally, authenticates callers by tailnet identity, and logs and meters usage.
  It is rejected as the gateway because:
  - It is a closed-source service hosted by Tailscale with no self-hosted option, and using your own provider keys outside its Personal plan needs a sales contract ([get started](https://tailscale.com/docs/aperture/get-started)).
  - Its [quotas](https://tailscale.com/docs/aperture/configuration) (per user, per node or shared) deduct the estimated cost after the response, and the last bucket in a chain can go negative; there is no worst-case reservation against a lease from Cantiere's daily counter, so COST-2's hard cap cannot be enforced.
  - Per-session attribution (COST-1) would mean mapping each ephemeral node's device ID back to its session and importing Aperture's usage records; Aperture's own session IDs come from the client inside the sandbox, so they cannot be trusted, and sessions without a tailnet node (ADR-0011) have no identity to call it with.
  - Provider keys would sit as literal values in Aperture's config instead of the secret store (ADR-0010).
  Aperture behind the worker's gateway, as one more upstream provider for deployments that already run it, is not covered by this decision.
  It would keep metering and budgets on the worker, but needs the worker itself on the tailnet; adding it takes a superseding ADR.
- **Gateway inside the worker process:** one process fewer and no worker-to-proxy protocol, but the code that parses sandbox-controlled traffic would run as root beside KVM, the jailer, nftables and every session's secrets.
- **Self-hosted open-source gateways** (evaluated 2026-10-21 against the gateway's required behaviour: unchanged passthrough, keys from OpenBao, per-session keys, reservation before forwarding, per-request cost, audit).
  None meets it in its free edition, and two requirements fail almost everywhere: reading provider keys from OpenBao without a restart, and an audit log, both either paid or missing.
  - [LiteLLM](https://github.com/BerriAI/litellm) `v1.106.1` (MIT, Python): reserves worst-case cost before forwarding by default, and `fail_closed_budget_enforcement` makes it refuse requests when spend cannot be checked, but its Vault integration and audit log need an enterprise licence; it caches keys for 60 s per worker process, so a deleted key keeps working on other workers; its unchanged-passthrough routes use one gateway-wide key resolved at load, so rotating it needs a restart; and its official image bundles the commercially licensed `enterprise/` code.
    It had a PyPI supply-chain compromise (`1.82.7`, `1.82.8`) and three CVEs in 2026.
  - [Bifrost](https://github.com/maximhq/bifrost) `transports/v2.3.2` (Apache-2.0, Go): Vault support and audit log are enterprise-only, and budgets are charged after the response with no reservation.
  - [agentgateway](https://github.com/agentgateway/agentgateway) `v1.6.0` (Apache-2.0, Rust, Linux Foundation): the best data plane of the set (unchanged passthrough, unbuffered streams, signed images, Postgres only), but budgets are charged after the response, there is no OpenBao client or audit log, and counters flush every 5 s.
    Combining it with a Cantiere budget service behind its external-authorization hook and OpenBao Agent was the closest composition and is rejected because agentgateway reads provider keys only inline from config or from files, so OpenBao Agent would have to render them to files (against ADR-0010), it adds three processes per deployment, the authorization hook sees only the first 8 KB of a request body by default, and settlement would come from asynchronous logs.
    It remains the fallback if this decision fails conformance test 9.
  - [Otari](https://github.com/mozilla-ai/otari) `v0.30.1` (Apache-2.0, Python): reserves worst-case cost in one atomic update and refuses unpriced models by default, which this decision's reservation follows, but it reads provider keys only from the environment at start, rebuilds requests through provider SDKs, and runs its own tools outside the session sandbox.
  - Agent Router (formerly Envoy AI Gateway) `v1.2.0`, Apache APISIX `3.19.0`, Kong Gateway OSS `3.9`, Portkey Gateway OSS, GoModel, Higress, TensorZero and Helicone's gateway fail more of it: paid secret-store support, no dollar budgets or per-caller keys in the free edition, Kubernetes-only production support, archived, or relicensed with a hosted-control-plane dependency.
- **The gateway-only service's egress proxy:**
  - A non-terminating filter, either a `CONNECT` target allowlist or routing on the TLS SNI (for example HAProxy in `mode tcp` or nginx `ssl_preread`), is rejected because on a shared CDN address a compromised gateway can send an allowed SNI with a different `Host` (domain fronting) or use Encrypted Client Hello, and reach a host absent from the list.
    HAProxy's manual says of `req.ssl_sni` that it "is not reliable enough to be used alone for allowing or denying access to certain hosts" ([HAProxy 3.4 configuration manual, section 7.3.5](https://docs.haproxy.org/3.4/configuration.html)).
    A `CONNECT` allowlist is weaker still: after a `CONNECT` the proxy relays bytes blindly ([RFC 9110, section 9.3.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6)), so any SNI can follow.
  - Among terminating reverse proxies, Caddy is chosen because it is Apache-2.0, verifies upstream certificates by default and defaults the TLS server name to the upstream's host ([`reverse_proxy`](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)), and the project's maintainer already operates it.
  - Reusing the session egress proxy (ADR-0011) is rejected because it is built for the sandbox's transparent interception, run-time allowlists, per-session CA and audit journaling, which the gateway-only service does not need, and extending its code for a fixed host list adds code Cantiere must maintain where an existing open-source proxy does the job.
  - Address-only filtering, the gateway reaching port 443 on the addresses its resolver returns, is rejected because an address set cannot tell apart hosts that share an address, so a host behind the same CDN as an upstream host stays reachable.
